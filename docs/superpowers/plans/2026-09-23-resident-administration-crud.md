# Resident Administration CRUD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the resident-directory prototype and mock authentication with a secure, PostgreSQL-backed administrator CRUD flow and mandatory resident first-login password change.

**Architecture:** ASP.NET Core controllers use the existing cookie/CSRF session model and delegate persistence to focused infrastructure services. Every resident query is scoped through `User -> Apartment -> Building.AdminId`, while the React frontend uses one same-origin API client and server-derived identity instead of `localStorage` sessions.

**Tech Stack:** .NET 10, ASP.NET Core controllers, EF Core 10, PostgreSQL 18, xUnit, Testcontainers, React 19, TypeScript 6, Vite 8, Vitest, Testing Library, vanilla CSS.

**Spec:** `docs/superpowers/specs/2026-09-23-resident-administration-crud-design.md`

## Global Constraints

- OpenProject work package: `#94` — Administrator Resident Directory & Directory Management.
- Authorization roles remain exactly `Admin` and `Resident`; never add `Proprietar` or `Chiriaș`.
- `DELETE` means logical deactivation; never hard-delete a resident.
- The backend, not the frontend route guard, is the security boundary.
- Resident and apartment access must be filtered by the authenticated administrator's buildings in the database query.
- Passwords must never be logged, returned, placed in URLs, or persisted in frontend storage.
- Use the existing safe error envelope, 16 KiB request limit, secure cookie settings, and CSRF contract.
- All commits follow Conventional Commits and end with `#94`.
- Preserve unrelated user changes and do not broaden the feature into building or apartment administration.
